## 1. ما تم تنفيذه فعليًا

### `POST /api/v1/dashboard/stores` — إنشاء متجر
- أي `PlatformUser` مصادَق يستطيع إنشاء متجر (لا يتطلب تحقق البريد — قرار نطاق موثَّق أدناه).
- **معاملة واحدة ذرّية** (`apps/stores/services.py:create_store`) تُنشئ: `Store` + `StoreDomain` (subdomain أساسي `{slug}.{PLATFORM_ROOT_DOMAIN}`) + `StoreMembership` (owner, active) — الثلاثة معًا أو لا شيء.
- `slug` مطلوب صراحةً من المستخدم (لا اشتقاق تلقائي من الاسم)، يُطبَّع lowercase، يُرفض إن كان محجوزًا (27 كلمة محجوزة: www, api, admin, dashboard...) أو مكرّرًا (فحص مسبق + قيد DB كضامن حقيقي ضد race condition).
- Rate limiting: 10 عمليات إنشاء/ساعة لكل مستخدم.
- `Store.id` مولَّد من الخادم (uuid7) دائمًا — لا يمكن للعميل "اختطاف" متجر موجود عبر تمرير id/store في الـ payload (مُثبَت باختبار صريح).

### `GET /api/v1/dashboard/stores/<uuid>` — تفاصيل المتجر
- يتطلب مصادقة + عضوية نشطة (`StoreMembership.status=active`) في **هذا** المتجر تحديدًا.
- **404** إن لم يوجد المتجر أصلاً، **403** إن وُجد لكن المستخدم ليس عضوًا فيه — تمييز متعمَّد يتّسق مع قرار Phase 1 (سياسة SELECT على `Store` مفتوحة عمدًا؛ وجود المتجر ليس سرًّا، فالتمييز بين 404/403 لا يُسرِّب معلومة جديدة).
- التحليل يعتمد على **المسار (path)** لا الـ Host header — مُثبَت باختبار: Host header يشير لنطاق مختلف تمامًا، والوصول ما زال يعمل بشكل صحيح بناءً على الـ path فقط.
- حُذفت نقطة `/api/v1/dashboard/stores/<uuid>/_debug` التشخيصية من Phase 1 لأن `StoreDetailView` الحقيقية تغطي نفس مسار الحلّ الآن (كما وعدت تقارير Phase 1/2). نقطة `_tenant/context` (Host-based) ما زالت مؤقّتة لعدم وجود storefront حقيقي بعد.

## 5. Bug حقيقي كبير اكتُشف وأُصلح جذريًا ⚠️

**هذا هو أهم اكتشاف في Phase 3 — يمسّ آلية RLS الأساسية من Phase 1 نفسها.**

اختبار `test_two_stores_by_the_same_user_get_two_independent_owner_memberships` فشل بخطأ PostgreSQL حقيقي غير متوقَّع:
```
psycopg.errors.InvalidTextRepresentation: invalid input syntax for type uuid: ""
```

**السبب الجذري:** كل سياسات RLS (منذ Phase 1) تقارن هكذا:
```sql
store_id = current_setting('app.current_store_id', true)::uuid
```
`apps.tenancy.db.clear_tenant_context_from_db()` يمسح السياق بضبط الـ GUC على **نص فارغ `''`** (وليس بإلغائه فعليًا — هذا مقصود، متوافق مع pgbouncer/الاتصالات الدائمة). لكن تحويل `''` مباشرة إلى `::uuid` في PostgreSQL **يرمي خطأً فعليًا**، ولا يُرجع `NULL` كما افترضتُ في Phase 1. أي استعلام عبر `.unscoped` (أو أي مسار مستقبلي يتجاوز الفلترة Python) في حالة "لا يوجد tenant" كان سيتحطّم بدل أن يُرجع صفرًا من الصفوف بأمان.

**التحقق المباشر من المشكلة والحل (وليس افتراضًا):**
```sql
SELECT set_config('app.current_store_id', '', true);
SELECT current_setting('app.current_store_id', true)::uuid;
-- ERROR: invalid input syntax for type uuid: ""

SELECT NULLIF(current_setting('app.current_store_id', true), '')::uuid;
-- NULL  ✅
```

**الإصلاح:** `NULLIF(current_setting(...), '')::uuid` بدل التحويل المباشر — عبر:
1. تحديث `apps/tenancy/rls.py` (الدالة المُولِّدة للسياسات — تصلح كل الجداول المستقبلية تلقائيًا).
2. **ترحيلين تصحيحيين جديدين** يُسقطان ويُعيدان إنشاء السياسات الفعلية المُطبَّقة فعلاً على `stores_store` و`stores_storedomain` (`stores.0002`) و`accounts_storemembership` (`accounts.0003`) — لأن تعديل ملف ترحيل قديم لا يُصحّح قاعدة بيانات طُبِّق عليها الترحيل فعلاً.
3. **3 اختبارات ارتداد دائمة جديدة** (`test_rls_null_safety.py`) تمنع تكرار هذا الخطأ مستقبلاً، بما فيها اختبار يقرأ `pg_policies` مباشرة ويتحقّق أن كل سياسة تقارن الـ GUC تستخدم `NULLIF` فعليًا.

**هل كان لهذا أثر إنتاجي حقيقي محتمل؟** نعم جزئيًا — أي طلب "بلا tenant" (مثل تسجيل الدخول، أو إنشاء متجر نفسه) يُشغِّل استعلام `.unscoped` على جدول TenantOwnedModel لاحقًا (مثلًا كود platform_admin مستقبلي) كان سيتحطّم بدل أن يتصرّف بأمان. أُصلح قبل أن يصل لأي مرحلة إنتاجية.

### أخطاء اختبار (وليست أخطاء إنتاجية) اكتُشفت أثناء تشخيص ما سبق
اختباران افترضا خطأً أن `.unscoped` يتجاوز RLS نفسها (وليس فقط الفلترة على مستوى Python) — بعد الإصلاح أعلاه توقّفا عن التحطّم لكن أرجعا نتائج فارغة بدل الصحيحة، مما كشف الافتراض الخاطئ في الاختبار نفسه. صُحِّحا لاستعلام كل متجر ضمن سياقه الصحيح (يطابق التصميم الموثَّق في `apps/tenancy/models.py`).

## 6. قرارات معمارية جديدة (لم تتطلب توقفًا — قابلة للعكس، أو امتداد مباشر لقرار Phase 1 معتمَد)

1. **إنشاء المتجر لا يتطلب تحقق البريد.** يتماشى مع "متجر خلال دقائق" من المتطلبات الأصلية. قابل للعكس بسهولة (شرط واحد يُضاف لاحقًا إن ظهرت إساءة استخدام).
2. **404 مقابل 403 لتفاصيل المتجر**: امتداد مباشر لقرار Phase 1 (سياسة SELECT على `Store` مفتوحة عمدًا لأن وجوده ليس سرًّا) — لم يُفتح قرار جديد، بل طُبِّق القرار الموجود بانسجام.
3. **لم تُبنَ نقطة "قائمة متاجري"** — يتوافق مع تأجيل Phase 2 لنفس السبب (يحتاج GUC ثانٍ أو دور platform bypass)؛ لم يُعَد فتح هذا القرار كما طلبت.
4. **استثناء import-linter اختباري إضافي** (`apps.tenancy.tests.* -> apps.accounts.models`) بنفس منطق ونمط استثناء Phase 2 — موثَّق بنفس المعيار، لا يُضعف عقد الإنتاج.

**لم يظهر أي قرار معماري عالي التأثير أو يصعب التراجع عنه** يستدعي التوقف لأخذ رأيك بحسب معيارك المحدَّد.

## 7. أجزاء لم يتم اختبارها فعليًا / قيود معروفة (بعضها مستمر من Phase 1/2)

- **Docker لا يزال غير مُختبَر فعليًا** (مستمر، لم يتغيّر).
- `/api/v1/_tenant/context` (Host-based) لا تزال تشخيصية مؤقّتة — ستُحذف عند وصول storefront حقيقي (Phase 6+).
- لا اختبارات E2E (متوقَّع، frontend لم يبدأ).
- لا نطاقات مخصَّصة (custom domains) — `StoreDomain.Kind.CUSTOM` موجود في المخطَّط لكن بلا تدفّق تزويد فعلي.
- اختبار التزامن الحقيقي (سباق فعلي بين طلبين متزامنين لنفس الـ slug عبر threads/processes حقيقية) لم يُبنَ — الاختبار الحالي يثبت أن قيد DB يرفض التكرار التسلسلي بشكل صحيح، وهذا القيد نفسه (UNIQUE constraint) هو ما يضمن السلامة تحت التزامن الحقيقي أيضًا بحكم طبيعته في PostgreSQL، لكن لم يُختبَر بخيوط متعددة فعليًا.

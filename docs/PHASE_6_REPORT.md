## 0. قرار معماري عالي التأثير عُرض واعتُمد قبل التنفيذ: ملكية السلة

عُرض عليك قبل أي كتابة كود: هل تُبنى `apps.customers` الكاملة (مصادقة storefront مستقلة بـJWT خاص، تعادل حجم Phase 2) الآن، أم سلة ضيف بلا حساب؟ اعتمدتَ **Guest-first Cart**: لا `apps.customers`، لا JWT مستقل لعالم storefront، لا تسجيل/دخول/تحقق بريد للعملاء — كل ذلك مؤجَّل لمرحلة لاحقة تحدّدها خارطة الطريق. مع قواعد أمنية صريحة لتوكن السلة (عشوائي، غير قابل للاشتقاق، مُخزَّن كـhash فقط، غير مُعامَل كمصادقة). نُفِّذت هذه القواعد حرفيًا (القسم 3).

## 1. ما تم تنفيذه فعليًا

### apps.pricing (طبقة حساب نقية، لا تعتمد على catalog)
- `TaxRate`: **VAT غير مُثبَّتة (hardcoded)** — معدَّل مُعرَّف من التاجر، بقيد DB يضمن **نشاطًا واحدًا فقط لكل متجر في آن واحد** (`UniqueConstraint` جزئي `WHERE is_active=true`).
- `Coupon`: كوبون واحد لكل سلة (لا تكديس)، نوعان (نسبة مئوية / مبلغ ثابت) بقيد DB **discriminated union** حقيقي (`CheckConstraint`) يمنع تعارض القيم. `times_used` موجود في المخطَّط لكن **لا يُحدَّث من عمليات السلة عمدًا** — توثيق صريح لماذا (سلال ضيف مهجورة لا يجب أن تستهلك حد استخدام كوبون).
- `calculator.py`: دوال نقية بلا أي كتابة DB — تقريب نقطة واحدة (`Decimal` + `ROUND_HALF_UP`)، خصم لا يتجاوز الإجمالي الفرعي أبدًا.
- واجهات Dashboard: `GET/POST .../pricing/tax-rates`، `.../pricing/coupons` — إدارة تاجر فعلية، وليست بيانات وهمية.

### apps.carts (سلة ضيف، Host-based)
- `Cart`/`CartItem`: `CartItem.unit_price_amount` **لقطة (snapshot)** عند الإضافة، وليست قراءة حيّة من Catalog — سعر السلة لا يتغيّر بصمت أثناء تصفّح العميل.
- أول سطح **storefront حقيقي** في المشروع (`StorefrontAPIView` جديد، Host-based، `AllowAny`) — يُمارِس فعليًا مسار تحليل Host الذي بناه Phase 1 ولم يُستخدَم من قبل بواجهة حقيقية.
- `POST .../cart/reprice`: **عملية DoD الحرجة** — تُحدِّث كل سطر من `ProductVariant` الحالي فعليًا (تلتقط تغيير سعر المتجر)، وتُسقِط الأسطر التي أصبح منتجها/متغيّرها غير نشط، ثم تُعيد حساب المجاميع.
- حُذفت نقطة `/api/v1/_tenant/context` التشخيصية أخيرًا (كانت موعودة بالحذف منذ Phase 1) — سطح Cart الحقيقي يُمارِس نفس المسار الآن. حُدِّثت اختبارات `test_middleware_http.py` لاستخدام endpoint حقيقي بدلها.

## 2. قواعد أمان توكن السلة — نُفِّذت حرفيًا

| القاعدة المطلوبة | التنفيذ |
|---|---|
| لا يُستخدَم Platform JWT كهوية سلة | `StorefrontAPIView` منفصل تمامًا عن `PlatformJWTAuthentication`؛ اختبار صريح يثبت أن JWT منصّة صالح لا يمنح وصولًا لسلة أحد |
| توكن عشوائي غير قابل للتخمين | `secrets.token_urlsafe(32)` (نفس آلية `PasswordResetToken`، استُخرجت لدالة مشتركة `apps/core/tokens.py`) |
| غير قابل للاشتقاق من `cart_id`/`store_id` | مُختبَر صراحةً |
| hash بدل تخزين السر | `token_hash` = SHA-256 hex، 64 حرفًا، مُتحقَّق أنه ≠ التوكن الخام |
| Cart tenant-scoped ومحمية بـRLS | `TenantOwnedModel` قياسي + عزل عام تلقائي (10 سيناريوهات جديدة) |
| منع الوصول لـCart متجر آخر حتى بتوكن صالح | **مُثبَت فعليًا**: توكن صالح 100% لمتجر B، مُرسَل أثناء طلب لمتجر A → RLS تجعله غير مرئي، تُنشأ سلة A جديدة، لا تسريب |

## 3. Concurrency — لماذا لا يوجد اختبار تزامن مخصَّص لهذه المرحلة (وهذا قرار مبرَّر، وليس إغفالًا)

كل عملية تعديل على `Cart` (`add_item`, `update_item_quantity`, `recalculate_totals`, ...) تستخدم `select_for_update()` داخل `transaction.atomic()` — نفس نمط الانضباط المعماري من Phase 5. **لكن**، خلافًا لـInventory (حيث السباق على مورد نادر بين عملاء مختلفين يعني بيعًا زائدًا حقيقيًا)، سباق داخل *نفس* السلة (نفس التوكن) هو بالأساس تبويبان من نفس المتصفح — خطر حقيقي أقل بكثير، ولا يوجد "مورد نادر مشترك بين عملاء" يتنافسون عليه هنا. الـlocking موجود دفاعًا في العمق (يمنع lost update حتى في هذا السيناريو الأقل خطورة)، لكن لم أفرض اختبار تزامن حقيقي بلا حاجة فعلية إليه — تمشّيًا مع "لا تضف functionality/tests غير مطلوبة لمجرد أنها كانت مفيدة في مرحلة سابقة."

## 7. Bugs حقيقية — لا يوجد bug إنتاجي كبير هذه المرة (بخلاف Phases 3-5)

هذه أول مرحلة لا يظهر فيها bug إنتاجي جوهري أثناء البناء — إشارة إيجابية لتراكم الانضباط (RLS null-safety، عزل قاعدة الاختبار، إلخ من المراحل السابقة). ما ظهر فعليًا كان أخطاء **في الاختبارات نفسها** أثناء كتابتها، صُحِّحت فورًا قبل الاعتماد عليها:
1. Fixture تصادم اسم نطاق: حاولتُ إنشاء `StoreDomain` يدويًا بنفس الاسم الذي يُنشئه `create_store` تلقائيًا بالفعل (نسيت أن Phase 3 توفّره تلقائيًا) — صُحِّح بإزالة الإنشاء اليدوي المكرَّر.
2. افتراض اختباري خاطئ: توقّعتُ أن `AllowAny` يعني تجاهل ترويسة Authorization المشوَّهة بالكامل — DRF يتحقّق من صحة أي بيانات اعتماد **مُقدَّمة** بصرف النظر عن `AllowAny` (سلوك صحيح ومقصود، وليس bug). صُحِّح الاختبار ليستخدم JWT منصّة **صالح فعليًا** لإثبات الخاصية المقصودة أصلاً: لا يمنح وصولًا لسلة.

## 8. القرارات المعمارية الجديدة

| القرار | السبب |
|---|---|
| Guest-first Cart، لا `apps.customers` الآن | مُعتمَد صراحةً قبل التنفيذ (القسم 0) |
| `CartItem` لقطة سعر، ليست قراءة حيّة | يمنع تغيّر سعر السلة بصمت؛ `reprice` هو الآلية الصريحة المطلوبة في DoD |
| `pricing` تطبيق منفصل، لا يعرف عن `catalog` | كوبون/ضريبة على مستوى السلة كلها فقط (لا قواعد لكل منتج)، حسب النطاق الأصلي |
| `Coupon.times_used` لا يُحدَّث عند التطبيق على السلة | يمنع سلال مهجورة من استنزاف حد كوبون محدود — سيُحدَّث عند إنشاء طلب فعلي (Phase 8) |
| `_tenant/context` حُذفت أخيرًا | وعد قائم منذ Phase 1، تحقّق أخيرًا بوجود مستهلك حقيقي |

## 9. ما تم اختباره فعليًا / ما لم يتم

**تم اختباره فعليًا**: كل تدفّق HTTP للسلة والتسعير ضد PostgreSQL حقيقي، أمان التوكن، عزل tenant (عام + HTTP)، سلوك RLS بلا context، القيود على مستوى DB لكل من TaxRate/Coupon/CartItem.

**لم يتم اختباره / خارج النطاق**:
- لا اختبار تزامن مخصَّص لعمليات السلة (مبرَّر، القسم 3).
- لا واجهة HTTP لتحديث سعر Variant مباشرة (لا تزال غير موجودة منذ Phase 4 — استُخدِم تعديل DB مباشر في اختبارات `reprice` لمحاكاة تغيير سعر التاجر).
- Docker غير مُختبَر فعليًا (مستمر).
- لا E2E بعد.

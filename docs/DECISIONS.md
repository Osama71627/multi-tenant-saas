# القرارات الهندسية المفتوحة — تحتاج موافقتك

هذه قرارات تؤثّر على **المعمارية الأساسية** ويصعب التراجع عنها لاحقًا. لكل قرار: الخيارات، الإيجابيات، السلبيات، وتوصيتي.

> يمكنك الردّ بـ: `D1: A, D2: B, ...` — أو ببساطة **"خذ بتوصياتك"** لاعتماد كل التوصيات.

## D1 — استراتيجية الـ Multi-Tenancy ⭐ (الأهم)

| الخيار | الإيجابيات | السلبيات |
|---|---|---|
| **A. Shared Schema + `store_id` + RLS** ✅ | أرخص، أسرع migrations، تحليلات المنصة بسيطة، يتوسّع لعشرات الآلاف من المتاجر، RLS يعطي ضمانًا على مستوى المحرّك | استرجاع بيانات متجر واحد يحتاج أداة مخصّصة؛ خطأ برمجي بلا RLS = تسرّب |
| B. Schema per Tenant | عزل بديهي، استرجاع/حذف متجر سهل | migrations تنهار بعد ~1–2k متجر (ساعات)، مشاكل مع pgbouncer، تحليلات المنصة مؤلمة |
| C. Database per Tenant | أقوى عزل ممكن | تكلفة عالية جدًا، عمليات معقّدة، لا يصلح لخطة مجانية |

**توصيتي: A** — مع بقاء الباب مفتوحًا لنقل متجر Enterprise ضخم لاحقًا إلى DB مخصّصة عبر Database Router دون تغيير أي كود domain.
**التبرير:** العزل هنا مفروض بخمس طبقات، أقواها RLS داخل PostgreSQL نفسه ← حتى لو نُسي فلتر في Python، المحرّك يرفض الصف.

## D2 — هوية العميل (Customer Identity)

| الخيار | الإيجابيات | السلبيات |
|---|---|---|
| **A. عميل منفصل لكل متجر** ✅ | عزل خصوصية تام بين تجّار متنافسين، بيانات العميل ملك التاجر، بريد واحد يصلح لعدّة متاجر | العميل يسجّل من جديد في كل متجر |
| B. هوية موحّدة عبر المنصة | تسجيل مرة واحدة، تجربة أفضل، بيانات موحّدة | متجر A قد يستنتج أن عميله يتسوّق من B؛ خطر خصوصية وامتثال؛ تعقيد صلاحيات كبير |

**توصيتي: A** — هذا ما تفعله Shopify. يمكن إضافة "Login with Platform" كطبقة اختيارية لاحقًا دون كسر النموذج.

## D3 — تخزين الـ JWT في Next.js

| الخيار | الإيجابيات | السلبيات |
|---|---|---|
| **A. BFF: كوكيز httpOnly تُدار في Next.js Route Handlers** ✅ | JS لا يرى التوكن ⇒ XSS لا يسرق الجلسة، تحديث مركزي، يعمل مع RSC | قفزة شبكة إضافية، حاجة لحماية CSRF |
| B. Access في الذاكرة + Refresh في كوكي | أقل قفزات | التوكن يُفقد عند التحديث، منطق متكرر في 3 تطبيقات |
| C. localStorage | الأبسط برمجيًا | ❌ أي XSS = سرقة كاملة للحساب. مرفوض لمنصة تتعامل مع أموال |

**توصيتي: A**.

## D4 — عرض الـ Storefront والتخزين المؤقت

| الخيار | الإيجابيات | السلبيات |
|---|---|---|
| **A. RSC + ISR مع إبطال موجّه بالوسوم (tag-based)** ✅ | سرعة صفحات ثابتة + بيانات طازجة، ممتاز لـ SEO، رخيص | يحتاج webhook إبطال من Django |

## D6 — نموذج الدفع (من يملك حساب المزوّد؟)

| الخيار | الإيجابيات | السلبيات |

| **A. كل تاجر يربط حسابه الخاص** ✅ (كما في المتطلبات) | الأموال تذهب للتاجر مباشرة، مسؤولية قانونية أقل علينا، نبقى في PCI SAQ-A | لا نستطيع اقتطاع عمولة لكل عملية تلقائيًا |

# Trusting the staging Caddy CA on Windows

**Scope: local staging/preview only.** This has no effect on production TLS
architecture, which is untouched by anything in this document.

## Why this is needed

`docker-compose.staging.yml`'s Caddy service uses `tls internal` (see the
comment block at the top of `infra/caddy/Caddyfile`): there's no real DNS
zone to run public ACME against for `*.lvh.me`, so Caddy issues certificates
from its own local CA instead. That CA is generated by the container itself,
inside the `staging_caddy_data` volume, the first time it starts — Windows
and Chrome have no reason to trust it by default, which is what produces
`ERR_CERT_AUTHORITY_INVALID` when browsing to `https://admin.lvh.me`,
`https://dashboard.lvh.me`, or any `https://<store>.lvh.me`.

The fix is to trust Caddy's **public** root certificate on the Windows host
— never its private key, and never by weakening TLS or switching to HTTP.

## Where the CA lives

Inside the running `caddy` container:

```
/data/caddy/pki/authorities/local/root.crt          <- public cert, safe to export/trust
/data/caddy/pki/authorities/local/root.key           <- PRIVATE KEY, never export this
/data/caddy/pki/authorities/local/intermediate.crt    (part of the chain Caddy serves; not needed in the trust store)
/data/caddy/pki/authorities/local/intermediate.key   <- PRIVATE KEY, never export this
```

`/data` is the `staging_caddy_data` named volume (see the `caddy` service in
`docker-compose.staging.yml`), so this CA persists across container
restarts and is only regenerated if that volume itself is removed
(`docker compose -f docker-compose.staging.yml down -v`, or a manual
`docker volume rm`).

## One-time setup (or after the CA regenerates)

```powershell
powershell -ExecutionPolicy Bypass -File infra\caddy\trust-local-ca.ps1
```

What it does, and why each step is scoped the way it is:

1. Finds the running `caddy` container (matched by name, so it works
   regardless of which directory `docker compose` was originally launched
   from).
2. Copies out **only** `root.crt` via `docker exec ... cat` — the private
   keys never leave the container.
3. Imports that cert into `Cert:\CurrentUser\Root` (the current Windows
   user's Trusted Root Certification Authorities store) via `certutil -user
   -addstore Root`. This is the store Chrome, Edge, and Windows' own
   `curl.exe` (Schannel) all consult, and — unlike the machine-wide
   `LocalMachine\Root` store — importing into it does **not** require
   administrator elevation, which is the least-privileged way to get there.
4. If a stale entry for the same CA subject but a different thumbprint is
   found (i.e. the CA was regenerated because the data volume was reset),
   removes the old entry first. Safe to re-run any number of times.
5. Confirms the installed entry's `HasPrivateKey` is `False` as a final
   sanity check that nothing beyond the public cert was imported.

## Verifying it worked

**Browser:** restart Chrome if it was already running (it caches TLS
validation results per-process), then visit each of:

- `https://admin.lvh.me`
- `https://dashboard.lvh.me`
- `https://demo-store-a.lvh.me`
- `https://demo-store-b.lvh.me`

Each should load the real app with a plain padlock, no interstitial
warning.

**curl.exe (Windows' bundled Schannel build):**

```powershell
curl.exe -s --ssl-no-revoke -o NUL -w "%{http_code}`n" https://admin.lvh.me
```

`--ssl-no-revoke` is required here and is expected, not a sign anything is
wrong: Schannel hard-fails revocation checking (CRLs/OCSP) by default, and a
private local CA has no revocation infrastructure to check against — the
same as any internal/enterprise CA. Chrome's own verifier soft-fails
revocation lookups by default, so this Schannel-specific flag has no
equivalent requirement in the browser.

## What this deliberately does NOT do

- Does not modify `infra/caddy/Caddyfile` or `docker-compose.staging.yml`.
- Does not disable HTTPS or fall back to plain HTTP anywhere.
- Does not install any private key (`root.key` / `intermediate.key`) on
  Windows — only the public `root.crt`.
- Does not touch the machine-wide `LocalMachine\Root` store — every other
  Windows user account on this machine is unaffected.
- Does not change anything about how production TLS is issued or terminated
  — this entire mechanism is specific to `docker-compose.staging.yml`'s
  local preview environment.

## Removing the trust later

```powershell
Get-ChildItem Cert:\CurrentUser\Root | Where-Object { $_.Subject -like "*Caddy Local Authority*" } | Remove-Item
```
